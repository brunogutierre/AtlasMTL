# AtlasMTL roadmap

## 1. Description

AtlasMTL is a natural-language geospatial assistant over Montreal open data. A visitor types a question in English or French. A Claude-backed agent decides which typed tools to call: find features, spatial joins and distances, counts per borough, geocoding. The tools run parameterized PostGIS queries. The answer streams back as text, a visible trace of the tool calls, and GeoJSON drawn on a MapLibre map.

### Example questions

- Schools within 1 km of a hospital
- Parks in Rosemont larger than 2 hectares
- How many health facilities per borough?
- What's near 1000 rue Sherbrooke Ouest?

### Build order and dependencies

- Built **after** [RecordBridge](https://github.com/brunogutierre/RecordBridge): the Angular API layer and the `AgentEvent` stream types are generated by it. RecordBridge needs SSE support (its PR 11) before AtlasMTL PR 10.
- Uses [Tessera](https://github.com/brunogutierre/Tessera) for its UI. Only released Tessera features are used; gaps become upstream issues, never forks or blockers.

## 2. Architecture decisions

| Decision | Choice | Why | Rejected |
|---|---|---|---|
| Agent framework | Spring AI 2.0 chat model + `@Tool` beans, with our own tool loop ([ADR 0009](docs/adr/0009-own-tool-loop.md)) | Native to Spring Boot 4, provider-agnostic, observability built in | LangChain4j (less Spring-native), a hand-rolled loop |
| Model | Fast, cheap Claude model by default (configurable), prompt caching if the prompt is long enough to qualify; a scripted model for keyless development and tests | Tool routing doesn't need the largest model; caching cuts demo cost | A single fixed model |
| Tool safety | Typed tools with enums and range checks (`meters ≤ 5000`, `limit ≤ 500`, max 6 tool steps); the LLM never writes SQL | No SQL injection or runaway queries, and behavior can be tested | Text-to-SQL |
| Tool results | The LLM receives a short summary plus a `resultId`; the full GeoJSON goes only to the client | Keeps tokens low and the context small | Sending GeoJSON to the model |
| Streaming | SSE over `POST` (`fetch` + `ReadableStream`); sealed `AgentEvent` = `Token \| ToolCall \| ToolResult \| Features \| Usage \| Done \| Error` | One-way traffic is enough; typed on both sides via RecordBridge | WebSockets (two-way not needed), `EventSource` (GET only), WebFlux everywhere |
| Server model | Spring MVC + virtual threads | Simple blocking code that still scales for I/O-bound LLM calls | Reactive stack |
| Data access | `JdbcClient` with explicit SQL (`ST_DWithin` on geography, `ST_Within`, `ST_Buffer`) | Spatial SQL stays visible and reviewable | JPA + Hibernate Spatial (hidden SQL, awkward spatial joins) |
| Ingest | Java `ingest` module run weekly by GitHub Actions cron: download → checksum (skip if unchanged) → normalize → replace the dataset's rows in one transaction | Decoupled from web uptime and memory; repeatable | Spring Batch (overkill), ogr2ogr (extra tool, normalization in SQL scripts), `@Scheduled` in the web app |
| Geocoding | Local Montreal address dataset with a `pg_trgm` index | Free, no usage-policy issues, fast | Public Nominatim (usage policy), paid geocoders |
| Map | MapLibre GL JS + OpenFreeMap tiles; colors from Tessera tokens | Vector tiles, handles large GeoJSON, no API key | Leaflet (raster-first), Mapbox (key, pricing), OpenLayers (heavier API) |
| Auth | None. The demo is public, and ingest runs only in CI | Nothing to protect, fewer moving parts | Bring-your-own API key (liability of handling other people's keys) |
| Hosting | One container (Spring serves the Angular build) on Render Starter + Neon free tier (PostGIS) | No cold starts, ~US$7/month, Neon branches for CI | Render free (cold starts ruin the demo), Supabase free (pauses idle projects) |

|---|---|
| `describe_categories` | none |
| `find_features` | `category`, `borough?`, `near?`, `limit ≤ 500` |
| `within_distance` | `sourceCategory`, `targetCategory`, `meters ≤ 5000`, `borough?` |
| `count_by_borough` | `category` |
| `geocode` | `text` |
| `get_borough` | `name` |

### Public demo cost controls

- Per-IP rate limit (Bucket4j) and per-IP daily token budget
- A global daily budget; when it runs out, the demo switches to the cached example gallery only
- At most 6 tool steps per question, and capped output tokens
- Gallery examples are precomputed and replayed as SSE (zero LLM cost)
- A hard spend limit in the Anthropic console

### Testing strategy

- Testcontainers `postgis/postgis` with fixture GeoJSON for every tool's SQL
- A scripted stub `ChatModel` for orchestration and SSE tests (deterministic, no API calls in CI)
- **Eval suite**: YAML golden questions with expected tool names, argument constraints and result-count ranges, run nightly or by hand against the real model with a budget, never on every PR. It publishes a pass-rate report.
- Angular: Vitest; Playwright with mocked SSE, plus axe

### Observability

- Spring AI Micrometer observations (tokens, latency per tool and per model), Actuator + Prometheus
- One `query_log` row per question, which feeds a public `/stats` page: questions asked, average cost, latency and eval pass rate

## 4. Extras

- **MCP server**: expose the same `@Tool` beans through the Spring AI MCP server starter, so Claude Desktop or any MCP client can query Montreal data. Cheap to add, and recruiters notice it.
- Pluggable cities (`CityPack` = dataset list + category mapping): Toronto, Québec City, Laval
- Saved and shared question permalinks
- Export results as GeoJSON or CSV
- Voice input (Web Speech API)
- Walking isochrones ("parks within a 10-minute walk") via Valhalla
- Charts in answers (counts per borough), styled with Tessera tokens
